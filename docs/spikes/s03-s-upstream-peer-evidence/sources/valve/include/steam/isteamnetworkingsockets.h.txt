419: 	/// Configure multiple outbound messages streams ("lanes") on a connection, and
420: 	/// control head-of-line blocking between them.  Messages within a given lane
421: 	/// are always sent in the order they are queued, but messages from different
422: 	/// lanes may be sent out of order.  Each lane has its own message number
423: 	/// sequence.  The first message sent on each lane will be assigned the number 1.
424: 	///
425: 	/// Each lane has a "priority".  Lanes with higher numeric values will only be processed
426: 	/// when all lanes with lower number values are empty.  The magnitudes of the priority
427: 	/// values are not relevant, only their sort order.
428: 	///
429: 	/// Each lane also is assigned a weight, which controls the approximate proportion
430: 	/// of the bandwidth that will be consumed by the lane, relative to other lanes
431: 	/// of the same priority.  (This is assuming the lane stays busy.  An idle lane
432: 	/// does not build up "credits" to be be spent once a message is queued.)
433: 	/// This value is only meaningful as a proportion, relative to other lanes with
434: 	/// the same priority.  For lanes with different priorities, the strict priority
435: 	/// order will prevail, and their weights relative to each other are not relevant.
436: 	/// Thus, if a lane has a unique priority value, the weight value for that lane is
437: 	/// not relevant.
438: 	///
439: 	/// Example: 3 lanes, with priorities [ 0, 10, 10 ] and weights [ (NA), 20, 5 ].
440: 	/// Messages sent on the first will always be sent first, before messages in the
441: 	/// other two lanes.  Its weight value is irrelevant, since there are no other
442: 	/// lanes with priority=0.  The other two lanes will share bandwidth, with the second
443: 	/// and third lanes sharing bandwidth using a ratio of approximately 4:1.
444: 	/// (The weights [ NA, 4, 1 ] would be equivalent.)
445: 	///
446: 	/// Notes:
447: 	/// - At the time of this writing, some code has performance cost that is linear
448: 	///   in the number of lanes, so keep the number of lanes to an absolute minimum.
449: 	///   3 or so is fine; >8 is a lot.  The max number of lanes on Steam is 255,
450: 	///   which is a very large number and not recommended!  If you are compiling this
451: 	///   library from source, see STEAMNETWORKINGSOCKETS_MAX_LANES.)
452: 	/// - Lane priority values may be any int.  Their absolute value is not relevant,
453: 	///   only the order matters.
454: 	/// - Weights must be positive, and due to implementation details, they are restricted
455: 	///   to 16-bit values.  The absolute magnitudes don't matter, just the proportions.
456: 	/// - Messages sent on a lane index other than 0 have a small overhead on the wire,
457: 	///   so for maximum wire efficiency, lane 0 should be the "most common" lane, regardless
458: 	///   of priorities or weights.
459: 	/// - A connection has a single lane by default.  Calling this function with
460: 	///   nNumLanes=1 is legal, but pointless, since the priority and weight values are
461: 	///   irrelevant in that case.
462: 	/// - You may reconfigure connection lanes at any time, however reducing the number of
463: 	///   lanes is not allowed.
464: 	/// - Reconfiguring lanes might restart any bandwidth sharing balancing.  Usually you
465: 	///   will call this function once, near the start of the connection, perhaps after
466: 	///   exchanging a few messages.
467: 	/// - To assign all lanes the same priority, you may use pLanePriorities=NULL.
468: 	/// - If you wish all lanes with the same priority to share bandwidth equally (or
469: 	///   if no two lanes have the same priority value, and thus weight values are
470: 	///   irrelevant), you may use pLaneWeights=NULL
471: 	/// - Priorities and weights determine the order that messages are SENT on the wire.
472: 	///   There are NO GUARANTEES on the order that messages are RECEIVED!  Due to packet
473: 	///   loss, out-of-order delivery, and subtle details of packet serialization, messages
474: 	///   might still be received slightly out-of-order!  The *only* strong guarantee is that
475: 	///   *reliable* messages on the *same lane* will be delivered in the order they are sent.
476: 	/// - Each host configures the lanes for the packets they send; the lanes for the flow

485: 	/// SteamNetworkingMessage_t::m_idxLane
