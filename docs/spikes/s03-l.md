# S03-L — Windows latency and pacing diagnosis

Status: **diagnosis complete; harness artifacts instrumented, no gameplay criterion weakened**
(8 October 2026). This is a contended Windows development-host result, not a production
latency acceptance result.

## Scope and method

S03-L instruments the existing S03-R baseline from input sampling through client apply/draw.
The fixture now records:

1. client sample and RPC-send call,
2. accepted input at the host RPC boundary,
3. host physics consumption,
4. host snapshot send,
5. client snapshot receipt,
6. client physics installation, and
7. the next drawn frame when a window can draw.

The analyzer correlates the first accepted input sequence for each of the 20 existing pulses.
All cross-process durations use the same-machine Windows system clock; no cross-machine clock
claim is made. Existing engine elapsed times still own gameplay criteria. Instrumentation is
limited to the first pulse segment so it does not add unbounded telemetry to the later collision,
expiry and recovery cases.

`tools/run_s03_r.py` gained bounded diagnostic controls:

- `--bypass-proxy` connects the baseline client directly to the host loopback port;
- `--high-resolution-timer` balances Windows `timeBeginPeriod(1)`/`timeEndPeriod(1)` around
  the run;
- `--max-fps`, `--low-processor-mode`, and `--disable-vsync` expose and retain effective
  process pacing settings.

The proxy remains the default. Proxy bypass is baseline-only. The timer request is explicit,
not a permanent process-global default. Each result records proxy mode and requested/effective
pacing. Source and result evidence is catalogued in
[`s03-l-evidence`](s03-l-evidence/matrix-summary.json).

## Environment and contention

The pinned engine was `4.8.dev7.official.c971f93e7` on Windows 11. Other lanes owned between
2 and 11 Godot processes before individual matrix cases. Per the task rule, **every timing in
this record is labelled contended**. Process counts changed between cases; therefore the matrix
is a diagnosis of stage location and possible pacing controls, not a controlled benchmark.
Technical failures were retained. They were predominantly the unchanged wall-stop/20-response
criteria under contention, not analyzer exceptions.

Two seven-case matrices compared proxied/default, direct/default, proxied/high-resolution timer,
proxied/60 FPS cap, proxied/low-processor mode, windowed/VSync, and windowed/VSync disabled.
They ran before the final rebase integrated the ratified world-relative movement/mouse-aim input
envelope; retained source hashes make that boundary explicit. The transport path, sequence
correlation and pacing controls were unchanged in purpose. Three representative technically
passing baseline rows were:

| Case | Godot processes before | Physics p95 | Sample→apply p95 | Result |
| --- | ---: | ---: | ---: | --- |
| proxied + 1 ms timer | 6 | 126 ms | 107 ms | PASS |
| proxied + low-processor mode | 3 | 111 ms | 92 ms | PASS |
| direct loopback, proxy bypassed | 8 | 257 ms | 250 ms | PASS |

A windowed/VSync case produced a 144 ms physics p95, 163 ms drawn-response p95 and 149 ms
correlated sample-to-draw p95, but failed the unchanged wall-stop criterion and had only 5/20
physics response samples. It is retained as diagnostic evidence, not an accepted result.
The VSync-disabled companion, despite starting with only two other Godot processes, had 0/20
responses and also failed the wall criterion. This rules out a safe conclusion that disabling
VSync improves latency.

## Per-stage budget

The technically passing proxied/high-resolution-timer baseline provides the cleanest complete
20-sample stage cut in the retained first matrix:

| Stage | p95 |
| --- | ---: |
| input sample → client send call | 1 ms |
| client send → host accepted RPC receipt | 19 ms |
| host receipt → host physics consumption | 16 ms |
| host consumption → snapshot send | 39 ms |
| snapshot send → client receipt | 21 ms |
| client receipt → physics installation | 26 ms |
| correlated sample → installation | 107 ms |

Stage percentiles are independent and therefore are not expected to sum to the end-to-end p95.
Headless runs have no draw callback; the retained windowed diagnostic measured apply→draw p95
at 20 ms. The passing low-processor row had a similar split (1/29/15/40/17/22 ms and 92 ms
sample→apply). This locates the ordinary floor across both engine service/physics cadence and
snapshot cadence, rather than in one Python sleep alone.

## Findings and disposition

### Proxy and Windows timer

Baseline proxy deliveries have zero scheduled impairment and recorded 0 ms delivery delay at
proxy precision. Bypassing the proxy did not remove the Windows floor: its technically passing
row was 257 ms physics p95. A 1 ms timer request produced one passing 126 ms row and one failing
303 ms row under different contention. Consequently:

- the proxy is **not** the sole cause of the 109–255 ms historical Windows baseline;
- `timeBeginPeriod(1)` is useful as a diagnostic control but is **not** proven as a fix and is
  not enabled by default; and
- direct mode remains available to separate future transport/pacing measurements from proxy
  scheduling.

### Engine pacing

Neither an explicit 60 FPS cap nor VSync disable was consistently beneficial in the contended
matrix. Low-processor mode produced one technically passing 111 ms row, but another run failed
at 281 ms. Windowed VSync supplied actual draw receipts and about one additional frame from apply
to draw, while the headless/default process had no draw evidence. The harness therefore records
these controls without silently changing its accepted defaults.

The large failed-case tails were usually in client→host service or host snapshot→client service,
not sample collection (0–2 ms). They tracked changing concurrent process load poorly enough that
an uncontended rerun is required before choosing a production pacing default.

### Provisional Windows allowance for prediction and S12

Until an uncontended named-hardware rerun replaces this result, prediction and S12 should budget
for a **300 ms p95 baseline authoritative loop allowance on this Windows development host**.
This rounds above the passing direct-loopback 257 ms and historical fixed headless 255 ms results.
It is a provisional platform/jitter allowance, not permission to add 300 ms of gameplay delay,
not a network-RTT budget, and not a latency acceptance threshold. Client prediction must mask the
local loop while authoritative corrections win; S12 history/reconciliation design must retain
enough timestamped state for this local scheduling tail in addition to its separately selected
network allowance.

## Expiry-boundary analyzer fix

The pending fix is **applied** without changing the criterion. `S03RMatch` records the exact held
input age used at the beginning of its authoritative physics decision. The analyzer now requires:

- previous decision age `<= 250 ms`,
- expiring decision age `> 250 ms`,
- neutral held state for later stale rows, and
- zero velocity at the transition.

It no longer compares a later `Proof._on_step` telemetry timestamp with the earlier Match receipt.
The offline regression deliberately gives the previous telemetry row an apparent age of 253 ms
while Match's actual decision age was 249 ms. The criterion passes only from the exact 249→253 ms
decision boundary; no one-tick tolerance was added.

A fresh contended adverse run with the 1 ms timer and low-processor mode passed all unchanged
technical criteria. Its three expiry transitions were 235→256 ms, 6→284 ms (a contended physics
gap), and 249→270 ms. Physics response p95 was 392 ms; this does not replace prior accepted
profile numbers. The retained result is
[`adverse-expiry-result.json`](s03-l-evidence/adverse-expiry-result.json).

## Post-rebase validation

After rebasing onto `s08-enet-bandwidth`, the merged world-relative movement/mouse-aim envelope
was preserved together with S03-L telemetry. A current-source contended baseline run (seven other
Godot processes before launch) used the explicit 1 ms timer and low-processor controls and passed
all unchanged technical criteria. Its physics p95 was 101 ms and its 20-sample correlated stage
p95s were 1/17/26/40/17/26 ms, with 90 ms sample→apply. Its single expiry transition was the exact
249→264 ms Match decision. This is a compatibility/quick validation, not an eighth matrix case or
an uncontended replacement measurement. The retained receipt is
[`post-rebase-baseline-result.json`](s03-l-evidence/post-rebase-baseline-result.json).
