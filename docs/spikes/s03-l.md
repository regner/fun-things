# S03-L — Windows latency and pacing diagnosis

Status: **review-1 findings corrected; diagnosis complete without weakening gameplay criteria**
(8 October 2026). This remains a contended Windows development-host result, not production
latency acceptance.

## Scope and method

S03-L instruments the existing S03-R baseline from input sampling through client apply/draw.
The fixture records:

1. client sample and RPC-send call,
2. proxy receive and forward boundaries for every UDP datagram,
3. accepted input at the host RPC boundary,
4. host physics consumption,
5. host snapshot send,
6. client snapshot receipt,
7. client physics installation, and
8. the next drawn frame when a safely capped window can draw.

The analyzer correlates the first accepted input sequence for each of the 20 existing pulses.
ENet datagrams are opaque, so proxy measurements are aggregate per direction rather than falsely
attributed to an input sequence. All cross-process durations use the same-machine Windows system
clock; no cross-machine clock claim is made. Existing engine elapsed times still own gameplay
criteria. Pulse instrumentation is bounded before the later collision, expiry and recovery cases.

`prototypes/s03_r/tools/run_s03_r.py` provides these bounded diagnostic controls:

- `--bypass-proxy` connects the baseline client directly to the host loopback port;
- `--high-resolution-timer` balances Windows `timeBeginPeriod(1)`/`timeEndPeriod(1)` around
  the run;
- `--max-fps`, `--low-processor-mode`, and `--disable-vsync` expose and retain process pacing;
- **every windowed run requires exactly `--max-fps 60`**. The runner rejects uncapped or
  differently capped windowed configurations before querying or launching Godot.

The proxy remains the default. Proxy bypass is baseline-only. The timer request is explicit,
not a permanent default. Each result records proxy mode and requested/effective pacing.

## Safety correction and invalidated evidence

Uncapped windowed rendering is forbidden on this laptop because earlier uncapped work caused
`DXGI_ERROR_DEVICE_REMOVED`. The first two S03-L attempts mistakenly ran their windowed rows with
`max_fps=0`. **Every timing and image from those four windowed rows is invalid and unsafe and is
not used anywhere in this disposition.** The retained matrix catalogue names them only in its
`invalidated_historical_evidence` section.

The original proxy also took one timestamp before `recvfrom()` and reused it as receive and
forward time. Same-poll baseline delivery therefore read zero by construction. All old proxy-stage
values are invalid. Historical non-proxy gameplay outcomes remain history, but no conclusion here
uses their old proxy delay field. The corrected proxy now timestamps immediately after
`recvfrom()`, immediately before and after `sendto()`, and retains distinct receive/delivery
records. A unit regression inserts a deliberate proxy-loop delay and requires it to appear.

The corrected matrix uses `max_fps=60` for both windowed/VSync rows. Its VSync-off row therefore
never renders uncapped. The committed before/after PNGs come from that safe capped row.

Its corrected aggregate proxy budget was:

| Proxy stage | Samples | p95 |
| --- | ---: | ---: |
| prior poll completion → `recvfrom()` return | 2,446 | 7.860 ms |
| `recvfrom()` return → `sendto()` return | 2,446 | 0.440 ms |

| upstream receive → forward | 1,308 | 0.502 ms |

The poll-gap value is an upper bound from the prior poll completion to receive return. It includes
runner scheduling and possible kernel residence, but Windows/Python does not expose the datagram's
exact kernel-arrival timestamp here. It must not be described as exact kernel wait. Receive-to-
forward and schedule-overrun values are measured from separate monotonic timestamps, not one
pre-receive timestamp. Stage percentiles are independent and are not expected to sum exactly to
the end-to-end p95.

## Blocking-call and proxy-loop audit

A follow-up audit checked S03-L specifically for the synchronous Windows contention-sampler defect
found in S11. `prototypes/s03_r/tools/run_s03_r.py` contains no `tasklist`, WMIC, PowerShell, CPU query, or other
contention sampler. Its external-process boundaries are:

- `engine_version()` runs before any case or proxy exists;
- isolated Godot import through `checked_command()` completes before `FootProxy` is constructed;
- host process creation occurs before polling starts;
- client process creation occurs inside the readiness loop, but before the client emits `start`,
  before `proxy.start` arms impairment timing, and before input measurement starts; and
- owned-child stop/wait/kill cleanup runs only after measurement exits or fails.

Inside the armed measurement loop, the runner performs bounded nonblocking proxy socket work,
reads appended local log files, calls nonblocking `Popen.poll()`, and takes the intentional 2 ms
sleep. The matrix wrapper's `tasklist` process count was sampled before each runner invocation,
not by the proxy process and not during its measurement window.

Therefore the S11 blocking-sampler defect is **not present in S03-L**, no call needed relocation,
and this finding does not trigger another matrix rerun. Corrected accepted raw proxy receipts also
show no multi-second loop excursion: maximum receive poll-gap upper bounds were 69.878 ms for the
high-resolution case, 39.908 ms for capped VSync on, and 120.637 ms for capped VSync off. These
observations do not rule out ordinary scheduler contention; they rule out the identified
multi-second synchronous-sampler mechanism in the retained accepted cases.

## Findings and disposition

### Proxy and Windows timer

Corrected zero-impairment proxy forwarding is sub-millisecond at p95 in the passing high-resolution
case. The default corrected proxy row similarly measured 0.426 ms receive-to-forward and 0.317 ms
schedule overrun, while its poll-gap upper bound was 8.648 ms. These measurements reject the old
“0 ms” claim and show that Python receive/forward work itself does not explain a 100–300 ms floor.
The 6–16 ms poll-gap tails can contribute scheduling delay, but they are not the full authority
loop.

Bypassing the proxy did not remove the floor: the corrected direct case passed at 317 ms physics
p95. Thus the proxy is **not the only possible source**. This does not prove the proxy has zero
cost. The 1 ms timer row passed at 119 ms, but its zero-unrelated-Godot launch count differs from
other rows, so `timeBeginPeriod(1)` remains a diagnostic control rather than a default fix.

### Engine pacing and safe VSync comparison

The safely matched windowed rows both used `max_fps=60` and started with three unrelated Godot
processes. VSync on/off passed all unchanged technical criteria:

| Setting | Physics p95 | Drawn response p95 | Sample→draw p95 | Apply→draw p95 |
| --- | ---: | ---: | ---: | ---: |
| VSync on, 60 FPS cap | 98 ms | 105 ms | 95 ms | 8 ms |
| VSync off, 60 FPS cap | 100 ms | 107 ms | 100 ms | 8 ms |

Within this one contended pair, disabling VSync produced no meaningful latency improvement. No
uncapped comparison is permissible. Headless FPS and low-processor rows were inconsistent under
changing contention, so the harness records controls without silently changing headless defaults.

### Provisional Windows allowance for prediction and S12

Until an uncontended named-hardware rerun replaces this result, prediction and S12 should budget
for a **350 ms p95 baseline authoritative-loop allowance on this Windows development host**. This
rounds above the corrected passing direct-loopback 317 ms result. It is a provisional scheduling/
jitter allowance, not permission to add delay, not a network-RTT budget, and not a latency
acceptance threshold. Prediction must mask the local loop while authoritative corrections win;
S12 history/reconciliation must retain enough timestamped state for this tail in addition to its
separately selected network allowance.

## Expiry-boundary analyzer fix

The pending fix remains applied without changing the criterion. `S03RMatch` records the exact held
input age used at the beginning of its authoritative physics decision. The analyzer requires:

- previous decision age `<= 250 ms`,
- expiring decision age `> 250 ms`,
- neutral held state for later stale rows, and
- zero velocity at the transition.

It no longer compares a later `Proof._on_step` timestamp with Match's earlier decision. The offline
regression gives the previous telemetry row an apparent age of 253 ms while Match's actual age was
249 ms. It passes only from the exact 249→253 ms decision boundary; no one-tick tolerance exists.

The retained adverse expiry run began with **zero unrelated Godot processes observed**. It is
still conservatively labelled contended because that count is only a launch-time process snapshot
and the workstation was not otherwise isolated. It passed all unchanged technical criteria with
three transitions: 235→256 ms, 6→284 ms after a physics gap, and 249→270 ms. Its 392 ms physics
p95 does not replace prior profile numbers. This run validates expiry, not corrected proxy timing.
