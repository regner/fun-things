# M1-A2.3 foot prediction and remote smoothing

M1-A2.3 adds production local foot prediction/reconciliation and remote foot
presentation smoothing to the authoritative match replication path.

## Deliberate S03-P port

The production implementation ports only the measured movement techniques from
S03-P:

- a bounded 120-command client replay history;
- host consumed-or-superseded input acknowledgements;
- authority restore followed by replay through the same `ActorMotion.step` rule;
- immediate collision-body correction with short visual decay, plus a large-error
  snap that clears replay;
- remote snapshot interpolation, authority blending, and 125 ms capped
  extrapolation.

The prototype fixture classes and synthetic movement model were not promoted.
Production uses `FootCommand`, `ActorMotion`, measured codecs, lifecycle
revisions, and the existing admission and replica-state owners. The fixed 16-byte
input packet carries a host-authorized recovery epoch. The A2.4-owned outer command
envelope supplies the session, match revision, and controlled `EntityRef` fence;
this lane does not duplicate that lifecycle rule inside its packet. Generation
changes clear client replay before the new life can move. Replay can only step
movement; it has no gameplay mutation or effect endpoint.

The measured movement row is versioned and carries full 3D position and velocity,
including authoritative height and fall velocity. Exceeding the replay/freshness
window sends a fixed 16-byte recovery probe. Authority advances that participant's
epoch only after observing a sequence beyond its 120-command window, at most once
per second, then atomically resets the host queue, collector sequence, and prediction
history. Epoch 255 saturates instead of wrapping, and recovery cannot reset another
participant's input.
The delayed old-generation regression and host queue invalidation will bind to
A2.4's `PlayerLifecycle` and command envelope after that prerequisite lands on
`main`.

## Bounds and evidence

History, host queues, packet size, extrapolation, and integration capture counts
are explicit bounds. Lifecycle generation, life, control, collision, and match
changes invalidate replay or smoothing context. The real-process harness runs a
direct ENet profile and seeded normal/adverse UDP delay, jitter, and loss
profiles, and reports replay size, acknowledgement, p95/max correction, remote
jump/hold, malformed-packet rejection, and process diagnostics. Optional
windowed screenshots are capped and written only to the selected external output
directory.

After review corrections, the canonical production checks passed with Godot
`4.8.dev7.official.c971f93e7`, GUT 9.7.1, all owned-script compilation, Python,
and 171/171 GUT tests green. Fresh direct, normal (75 ms one way, 30 ms jitter,
2% loss), and adverse (125 ms one way, 50 ms jitter, 5% loss) ENet runs passed
after structured host/input readiness receipts with no diagnostics. Their client
p95 corrections were 0.018/0.360/0.480 m, post-recovery maximum corrections were
1.015/0.864/0.718 m, retained histories were 3/15/15 of 120, and maximum remote
frame jumps were 0.134/0.193/0.207 m. The deliberately forced 120-frame outage
produced bounded 10.083/10.083/10.084 m recovery corrections before movement
resumed without reconnecting. An additional adverse windowed run passed and
produced three PNG continuity frames in its external evidence directory.

No Godot MCP editor mutation tool was exposed in this worker environment. This
lane does not change editor-authored scenes or resources; scripts and tests were
therefore edited directly, then checked with the repository-pinned formatter,
headless Godot compilation/import, unit/production checks, and real-process ENet
runs.
