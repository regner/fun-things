## Question and decision proposal

For hitscan fired by a predicted local player at remotely interpolated entities, should
the host query current state, rewind bounded target history to the shooter's view, or
accept a client hit claim?

**Proposal for M1:** use host-authoritative, target-only lag compensation for pistol and
SMG, bounded to **250 ms**. The client sends a ShotId/fire intent, aim direction and a
view/snapshot reference; it never sends target, damage or a hit result in the production
codec. The host first validates life/seat/equipment, ammo/reload, fire cadence, aim and
ShotId, then ray-tests current static world plus dynamic target hit shapes restored to
the bounded view time. Restore history immediately after the query. A view older than
250 ms clamps to the floor; never expand the bound or trust a claimed hit to hide poor
adverse-network behavior.

This is shooter-favoring within a deliberate bound. A victim can already have moved from
the historical ray, so feedback must distinguish a local provisional impact from the
host verdict. The adverse fast-car result below shows that 250 ms cannot reconstruct an
approximately 350+ ms-old client view. That is an accepted degraded case, not evidence
to increase the rewind window silently.

For rockets, show a local cosmetic projectile immediately, keyed by ShotId. Replicate the
host launch parameters and authoritative contact/expiry; reconcile or replace the
cosmetic flight, and never predict damage/blast/chain outcomes. S05 remains the sole
damage/chain owner.

## Research

- Valve's client/server latency paper describes client prediction, entity interpolation
  and server lag compensation by moving players back to their positions when the command
  was generated: [Latency Compensating Methods in Client/Server In-game Protocol Design
  and Optimization](https://developer.valvesoftware.com/wiki/Latency_Compensating_Methods_in_Client/Server_In-game_Protocol_Design_and_Optimization).
- Valve's Source documentation makes the fairness trade explicit: the server evaluates a
  shot against historical player positions, subject to a configured maximum lag window:
  [Source Multiplayer Networking](https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking).
- Gabriel Gambetta's worked client/server series explains why the server must reconstruct
  what the shooter saw, while retaining server authority:
  [Lag Compensation](https://www.gabrielgambetta.com/lag-compensation.html).
- Glenn Fiedler describes buffering snapshots to interpolate remote presentation and the
  resulting latency trade: [Snapshot Interpolation](https://gafferongames.com/post/snapshot_interpolation/).
- Godot documents RPC authority, transfer modes and channels used by this fixture:
  [High-level multiplayer](https://docs.godotengine.org/en/latest/tutorials/networking/high_level_multiplayer.html).
  A reliable RPC is not permission to trust payload identity or gameplay outcomes.

These sources establish the architecture pattern, not this project's tuning, CPU cost,
history size or security limits.

## Options compared

| Option | Benefits | Costs and M1 fit |
| --- | --- | --- |
| A. Host query at receipt time | Smallest state and query cost; host reality always wins | Penalizes the shooter for network delay plus remote interpolation. Normal results had only 55%/44% median agreement for pedestrian/car targets. Reject for M1 hitscan feel. |
| B. Host rewinds dynamic target hit shapes, bounded to 250 ms | Host still owns verdict; substantially closer to the shooter's delayed view in the normal profile | Shooter-favoring; needs timestamp/snapshot validation, bounded history, temporary query state and current-world policy. Normal median agreement rose to 89%/63%. **Recommend.** |
| C. Client claims hit, host checks plausibility | Lowest apparent hit latency and can tolerate very old views | A compromised client chooses outcomes; plausibility tends toward reimplementing rewind while leaving ambiguous authority. Reject. The local `client_hit` field exists only to score this experiment and is never used for damage. |

A full-world rollback is unnecessary for M1 and much riskier than target-only history.
Static obstruction stays current. Destructible/moving collision would need an explicit
historical-world policy before it could be included.

## Prototype and boundaries

[`prototypes/s12/tests/fixtures/s12/boot.tscn`](../../prototypes/s12/tests/fixtures/s12/boot.tscn) inherits the saved
S03 boot. S03's `Session`, `Match`, `Replication` and `S03Transport` files are copied
read-only by the runner. The saved S12 scene adds one combat node and two instances of a
saved rail target: pedestrian-like 1.5 m/s with 0.45 m radius, and car-like 12 m/s with
1.0 m radius. The client buffers replaceable 20 Hz snapshots and aims from a view held
at least 100 ms after receipt. Deterministic edge offsets create both perceived hits and
misses.

The host retains at most 24 physics samples, clamps the requested view to 250 ms, and
returns both A and B verdicts for independent scoring. It validates exact intent shape,
512-byte application size, sender admission/session/revision, normalized finite aim,
monotonic sequence/window, 100 ms fire interval, 30-round magazine and 1.8 s reload.
Duplicate, nonfinite and oversized requests traverse the actual RPC boundary. Rockets
use a 1 s host cooldown and 18 m/s cosmetic speed. No target selection or client verdict
causes damage.

The fixture was text-authored because the Godot editor/MCP tools were unavailable, as
allowed by the lane brief. The pinned engine imported scripts, generated `.uid` sidecars,
and headlessly loaded/resaved both new scenes; `ResourceSaver.set_uid` assigned their
saved UIDs. This fallback does not claim synchronization with an open editor (none was
running).

[`prototypes/s12/tools/run_s12.py`](../../prototypes/s12/tools/run_s12.py) stages only S03/S12 into a fresh addon-free
project, imports it, launches separate host/client processes, and routes native ENet UDP
through the seeded S03 proxy. Normal is 75 ms ±30 ms one-way with 2% independent loss;
adverse is 125 ms ±50 ms with 5% loss, the proxy's actual one-second delivery
interruption, and a 250 ms host stall at authoritative tick 600. The 96-shot schedule
keeps ordinary fire and rockets active across both events. Adverse success requires one
blackout begin/end spanning at least 950 ms, at least one blackout traffic drop and an
observed host stall of at least 250 ms. Output must be fresh and outside the checkout. Child cleanup uses the
existing owner-only S03 helper. The analyzer and these runner criteria are independently
covered by [`test_s12_analysis.py`](../../tools/test_s12_analysis.py).

## Results

Three complete repetitions per profile passed. All timing is a **contended upper bound**:
other lanes were active. Concurrent Godot counts were normal 7/4/10 and adverse 11/9/13;
recorded CPU load was normal 65/0/1% and adverse 74/70/77%. The 0% sample is the Windows
instantaneous counter, not proof of an idle machine. Each adverse trace contains one
1000.9/998.3/1000.2 ms blackout with 38/35/37 drops; measured host stalls were
265/278/266 ms.
Raw results, proxy schedules and host/client logs are catalogued in
[s12-evidence](s12-evidence/README.md); aggregate
values are in [`aggregate.json`](s12-evidence/aggregate.json).

Agreement means `client perceived hit == host verdict`. “False positive” is the requested
metric: host says hit where the client perceived a miss. Rates below are median across
three repetitions; “worst” is the lowest repetition.

| Profile / target | Accepted samples | Host-current agreement median / worst | 250 ms rewind agreement median / worst | Current / rewind false positives, total |
| --- | ---: | ---: | ---: | ---: |
| Normal pedestrian 1.5 m/s | 94 | 54.5% / 48.5% | **89.3% / 81.8%** | 19 / 10 |
| Normal car 12 m/s | 102 | 43.8% / 40.0% | **62.5% / 57.1%** | 1 / 20 |
| Adverse pedestrian 1.5 m/s | 90 | 36.7% / 35.5% | **60.0% / 58.1%** | 18 / 18 |
| Adverse car 12 m/s | 89 | 43.3% / 37.9% | 44.8% / 23.3% | 3 / 9 |

Normal rewind is materially better for both speeds, but the higher normal car false
positives show the shooter-favoring cost even while total agreement improves. Every
adverse accepted view was clamped in these samples. Rewind helped the pedestrian but did
not help the fast car; that result is the main reason to keep the bound explicit and
report degraded old-view shots rather than claiming universal compensation.

| Bounded cost | Normal median / worst repetition | Adverse median / worst repetition |
| --- | ---: | ---: |
| Rewind query CPU p95 | 122 / 216 µs | 36 / 201 µs |
| Serialized Variant history peak | 2,988 / 2,988 bytes | 2,988 / 2,988 bytes |
| Predicted rocket launch offset p95 | 2.016 / 2.088 m | 24.192 / 30.510 m |

The CPU query touches one of two simple circles and is not a production broadphase or
capacity result. History bytes are Godot Variant bytes for two targets, not packed
production storage and not a linear capacity promise. The adverse rocket outlier came
from delayed authoritative launch timing under lossy reliable delivery; it demonstrates
why the cosmetic needs a bounded correction/hide policy rather than validating flight
quality. No projectile impact, S05 blast, rendering or readability was measured.

Across each successful case, all 96 ordinary shot attempts received a verdict; 59–68
were accepted depending on host fire/reload timing. Independently retained probe rows
were exactly `STALE_SEQUENCE` for duplicate sequence 96 and `INVALID` for nonfinite
sequence 97 and oversized sequence 98 in all six cases. The runner asserts those rows
without counting ordinary rate/reload rejections. History stayed at 24 samples and
2,988 bytes. Source fingerprints remained unchanged in each staged project, both
processes exited zero, and retained runtime logs had no engine or script diagnostics.

## Starting gameplay values for owner review

These are deliberately reviewable M1 starting values, not ratified balance:

| Definition | Health/damage and cadence | Capacity/range |
| --- | --- | --- |
| Player and pedestrian | 100 health | Host lifecycle owns death/3 s respawn for players |
| Car | 100 health | S05 destruction transition owns terminal outcome |
| Pistol | 34 damage, 0.25 s fire interval | 12 rounds, 1.4 s reload, 45 m range |
| SMG | 12 damage, 0.10 s fire interval | 30 rounds, 1.8 s reload, 35 m range |
| Rocket | 100 direct/blast damage through S05, 1.0 s cooldown | 18 m/s, 2.5 s lifetime, 4.1 m S05 radius |

Reserve ammo is unlimited. Spawn supplies all three weapons with full magazines and an
available rocket cooldown. Friendly fire and self-damage are always enabled. Firing and
reloading while seated remain forbidden.

For car-pedestrian impact, start with authoritative relative closing speed at contact:
no damage below 6 m/s; 25 damage at 6 m/s, linear to 100 at 14 m/s, capped at 100, with a
0.5 s per car/target contact cooldown. Use the host's contact and velocity, never a
client impact claim. This threshold/curve needs S04 body and population contact tests;
no car-ped contact was prototyped here.

## Production requirements

1. WeaponState owns selected weapon, per-weapon magazine/reload/cooldown and monotonic
   ShotId. Validate alive, unseated, revisions, aim/muzzle, ammo and capacity before a
   ShotId is committed; switching cannot reset timers.
2. DamageResolver accepts each committed ShotId once. Clients submit fire intent only;
   the host chooses hit target, damage and S05 request. Prediction/replay emits no damage,
   ammo mutation or duplicate effects.
3. Keep a packed, fixed-capacity history only for lag-compensated dynamic hit shapes.
   Store host tick/time and lifecycle/generation. Clamp to 250 ms, reject stale identity,
   bound candidates/query work, restore query state even on failure, and instrument cost.
4. Define timestamp/snapshot validation without trusting a client clock. Prefer the last
   host snapshot/tick demonstrably available to that participant plus bounded interpolation
   offset. Do not allow a future view or let repeated old views bypass cadence.
5. Query current static world and rewound dynamic targets in one explicit order. Record
   the shooter-favoring policy in feedback/telemetry. Do not rewind health, seats, wreck
   state, projectiles or the whole physics world.
6. Replicate reliable ShotId outcomes and readable muzzle/tracer/impact events. Local
   provisional feedback must be retractable/subordinate to the host verdict; remote
   interpolation remains presentation-only.
7. Spawn rockets authoritatively with ShotId, launch tick/pose/velocity and expiry. A
   local cosmetic launch may lead; host contact/expiry and S05 blast always win. Bound
   16 active rockets and define correction, rejection and late-join hydration behavior.
8. Apply sender-derived admission/context, exact codec/type/finite checks, packet/rate/
   sequence/queue bounds and repeated-abuse policy before gameplay mutation. Reliable
   delivery is not authentication and must not create an unbounded action queue.
9. Host death stops input/reload/fire, clears seats, then after 3 s uses the canonical
   bounded safe-spawn search. Restore full health/loadout before publication; report
   `SPAWN_BLOCKED` rather than overlap. No firing from cars.
10. Test pistol/SMG/rocket, self/friendly fire, peds/cars, death/respawn, reset and late
    join through production APIs under normal/adverse profiles, four players and M1
    population/effect limits. Measure packed history memory and full host simulation
    p95/p99 inside the 4/8 ms tick budgets.

## Proven, not proven, and open questions

Proven only for this fixture: actual separate-process ENet admission; bounded sender/
shape/sequence/cadence/ammo rejection; current and 250 ms target-history queries; three
normal/adverse repetitions; finite simple-query CPU/history; and rocket launch-offset
observation. The experiment does **not** prove production collision shapes, world
obstruction, damage/S05 integration, local movement replay, graphical feedback, car-ped
contacts, safe respawn, four-player capacity, sustained budgets, exports or hardware.

Owner review is needed for the proposed weapon/impact values and whether the explicit
250 ms shooter-favoring window is acceptable. No decision is needed to preserve the
architectural recommendation: client-claimed damage remains rejected.

Suggested TODO one-liner: **M1-B2 — Implement host-owned pistol/SMG hitscan with bounded
250 ms target-history lag compensation, ShotId/ammo validation, predicted rocket
presentation, S05 damage handoff and safe respawn acceptance.**

Suggested task-requirements bullet: **S12 evidence selects bounded target-only hitscan

snapshot references, packed history/query work, weapon state, rocket reconciliation,
S05 handoff, car-ped impact and 3 s safe respawn at four-player capacity.**
