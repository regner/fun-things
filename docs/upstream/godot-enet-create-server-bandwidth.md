## Summary

`ENetMultiplayerPeer::create_server` passes its computed channel count to
`ENetConnection::create_host_bound` as incoming bandwidth, passes `0` as the channel limit, and never
passes `p_in_bandwidth`. With `max_channels = 4`, the server therefore advertises an incoming limit of
6 bytes/s; at the next one-second ENet bandwidth epoch, a sending client's throttle can fall from 32
to 1 and discard about 30 of every 32 unreliable client-to-server packets. Any nonzero server
`max_channels` is affected, including the pinned `4.8.dev7` engine and current `master`. Until a fixed
engine is used, create the server, immediately restore the intended limits through
`host.bandwidth_limit`, and only then allow clients to connect.

### The arguments are shifted

At the [pin, lines 62–67](https://github.com/godotengine/godot/blob/c971f93e7e76b0ef919bf6009e7b868bea04db7f/modules/enet/enet_multiplayer_peer.cpp#L62-L67),
`create_server` declares `p_in_bandwidth` but calls:

```cpp
host->create_host_bound(bind_ip, p_port, p_max_clients, 0,
        p_max_channels > 0 ? p_max_channels + SYSCH_MAX : 0, p_out_bandwidth)
```

The same call is present in the inspected
[`master` snapshot, lines 62–67](https://github.com/godotengine/godot/blob/65e8d16951d6963cb3984c090e45f40d1ba5f704/modules/enet/enet_multiplayer_peer.cpp#L62-L67).
The callee's actual order is visible at the
[pin, lines 46–67](https://github.com/godotengine/godot/blob/c971f93e7e76b0ef919bf6009e7b868bea04db7f/modules/enet/enet_connection.cpp#L46-L67)
and the inspected
[`master`, lines 46–67](https://github.com/godotengine/godot/blob/65e8d16951d6963cb3984c090e45f40d1ba5f704/modules/enet/enet_connection.cpp#L46-L67):

```cpp
Error ENetConnection::create_host_bound(const IPAddress &p_bind_address, int p_port,
        int p_max_peers, int p_max_channels, int p_in_bandwidth, int p_out_bandwidth)
```

The consequences are exact:

- `p_max_channels + SYSCH_MAX` lands in `p_in_bandwidth`. `SYSCH_MAX` is 2, so the project's four
  application channels become an advertised incoming limit of **6 bytes/s**.
- `0` lands in `p_max_channels`; ENet interprets zero as its maximum channel count, so the requested
  channel limit is not enforced.
- `p_in_bandwidth` is never passed. This part is wrong for every server call, even when
  `max_channels == 0` happens to preserve unlimited bandwidth.
- A damaging throttle appears for any `create_server` call with `max_channels > 0` once a client
  sends more than the resulting few bytes per second.

GitHub commit history traces the bad call to
[`f39547b9bdb6a09917845e7bf8ee04d64f96c582`](https://github.com/godotengine/godot/commit/f39547b9bdb6a09917845e7bf8ee04d64f96c582)
(`[Net] Refactor ENetMultiplayerPeer to use ENet wrappers`, 15 July 2021). Before that refactor, server
creation passed channel count and both bandwidth values directly to `enet_host_create` in the correct
positions.

### ENet applies the advertised limit once per bandwidth epoch

ENet's [`enet_host_bandwidth_throttle`, pin lines 339–407](https://github.com/godotengine/godot/blob/c971f93e7e76b0ef919bf6009e7b868bea04db7f/thirdparty/enet/host.c#L339-L407)
(the same code in the inspected
[`master`, lines 339–407](https://github.com/godotengine/godot/blob/65e8d16951d6963cb3984c090e45f40d1ba5f704/thirdparty/enet/host.c#L339-L407)) first waits for
`ENET_HOST_BANDWIDTH_THROTTLE_INTERVAL`:

```c
if (elapsedTime < ENET_HOST_BANDWIDTH_THROTTLE_INTERVAL)
  return;
```

For a peer that advertises nonzero incoming bandwidth, it then calculates:

```c
peerBandwidth = (peer -> incomingBandwidth * elapsedTime) / 1000;
peer -> packetThrottleLimit = (peerBandwidth *
                                ENET_PEER_PACKET_THROTTLE_SCALE) /
                               peer -> outgoingDataTotal;
if (peer -> packetThrottleLimit == 0)
  peer -> packetThrottleLimit = 1;
```

The interval is 1,000 ms. It is a host epoch, not a timer started when this particular peer finishes
connecting, so the first collapse may happen less than a second after connection. Retained S08
telemetry observed it after 366 ms. If traffic becomes sparse after throttling, later bandwidth epochs
can restore 32 and then clamp again; the MRP records the minimum across its run so that this oscillation
cannot hide the defect.

The limit of 1 is applied on the **client's peer for the server**, because the server advertised its
bogus incoming limit during connection. ENet's unreliable-send path increments a counter modulo the
scale and discards the command whenever the counter exceeds the current throttle. See
[`protocol.c`, pin lines 1521–1552](https://github.com/godotengine/godot/blob/c971f93e7e76b0ef919bf6009e7b868bea04db7f/thirdparty/enet/protocol.c#L1521-L1552)
and the inspected
[`master` snapshot](https://github.com/godotengine/godot/blob/65e8d16951d6963cb3984c090e45f40d1ba5f704/thirdparty/enet/protocol.c#L1521-L1552):

```c
peer -> packetThrottleCounter += ENET_PEER_PACKET_THROTTLE_COUNTER;
peer -> packetThrottleCounter %= ENET_PEER_PACKET_THROTTLE_SCALE;

if (peer -> packetThrottleCounter > peer -> packetThrottle)
{
   /* remove and destroy this unreliable outgoing command */
   ...
   continue;
}
```

The scale is 32 and the condition is strictly `>`. A throttle of 1 therefore permits
counter positions 0 and 1, or about 2 of every 32 packets, and drops about 30 of
32 before they reach the network.
Reliable traffic follows a different path and is not discarded by this check, which is why an
application can stall waiting for a reliable response to an unreliable request the server never
received.

## How the project found it

The [S08 Windows observation](../spikes/s08-windows-observation.md) investigated an exported fixture
that stalled on a client-to-server `_held` RPC. The request used `unreliable_ordered` channel 2; the
reliable result never arrived because the host never saw the request. Scratch-only
[throttle telemetry](../spikes/s08-windows-evidence/throttle-telemetry/) showed the client's
`PEER_PACKET_THROTTLE_LIMIT` fall from `PACKET_THROTTLE_SCALE` (32) to 1 immediately before the lost
send. Setting RTT throttle deceleration to zero did not prevent it, which separated bandwidth
throttling from the normal RTT/jitter throttle. Tracing the advertised limit back through Godot's
wrapper exposed the shifted arguments above.

The retained evidence catalogue is
[`docs/spikes/s08-windows-evidence/README.md`](../spikes/s08-windows-evidence/README.md). In
particular, it links the pre-fix stalls, scratch source diff, fixed exported release/debug runs, and
five fixed minimal S03 runs. The project proof also independently checks that the client peer's
`PEER_PACKET_THROTTLE_LIMIT` remains equal to `PACKET_THROTTLE_SCALE`.

## Explain it like I'm 5

The server fills in a form with two neighboring boxes: “how many roads may we use?” and “how many
bytes may you send me each second?” Godot puts the number of roads into the bytes box. Asking for four
roads becomes “please send me only six bytes per second.” About once a second, the client's traffic
helper reads that tiny number and throws away almost every throw-away message before sending it. The
workaround erases the accidental speed limit before anyone connects.

## Workaround and contract

For this project's intended unlimited ENet host, call the workaround immediately after successful
server creation and **before any peer can connect**:

```gdscript
var peer := ENetMultiplayerPeer.new()
var error := peer.create_server(port, max_clients, max_channels)
if error == OK:
	peer.host.bandwidth_limit(0, 0)
```

This is the current fixture contract in
[`S03Transport.open_host`](../../tests/fixtures/s03/transport.gd): the native-peer owner performs the
call before publishing `peer_ready`. Every future M1-A1 ENet adapter must keep that ordering until the
selected engine contains and verifies the upstream fix. If the application intentionally wants finite
bandwidth, pass the intended incoming and outgoing byte-per-second values to `bandwidth_limit` instead
of `(0, 0)`.

Limits of the workaround:

- `(0, 0)` deliberately removes both ENet host bandwidth limits; it is only correct where unlimited
  bandwidth is intended.
- Applying it after peers connect is too late for the initial advertised value and permits an
  avoidable throttle interval. Do not rely on a later bandwidth update as the normal path.
- It does not make unreliable RPCs reliable, remove ordinary ENet congestion control, or justify
  waiting forever for a result from one unreliable request.
- It does not restore the requested channel cap in the affected engine. The bad call still created
  the host with ENet's maximum channel limit.
- Once a fixed engine is selected, retain a regression assertion on the client's throttle and review
  whether the explicit limit call remains part of the adapter's configured policy.

It runs a server and client in one headless process on loopback, polls both peers, sends a 512-byte
unreliable packet each frame for about 2.25 seconds, and reads the client's
`PEER_PACKET_THROTTLE_LIMIT` for peer 1. Run from the repository root with the pinned engine on `PATH`:

```sh
godot --headless --max-fps 60 \
  --path docs/upstream/godot-enet-create-server-bandwidth-mrp \
  --script main.gd
godot --headless --max-fps 60 \
  --path docs/upstream/godot-enet-create-server-bandwidth-mrp \
  --script main.gd -- --workaround
```

Actual pinned-engine output without the workaround:

```text
START mode=defect channels=4 workaround_before_connect=false
SAMPLE elapsed_s=0.50 throttle_limit=32/32 sent=31 received=30
SAMPLE elapsed_s=1.00 throttle_limit=1/32 sent=61 received=54
SAMPLE elapsed_s=1.50 throttle_limit=1/32 sent=91 received=56
SAMPLE elapsed_s=2.01 throttle_limit=32/32 sent=121 received=58
RESULT mode=defect elapsed_s=2.26 minimum_limit=1 final_limit=32 scale=32 sent=136 received=59
```

Actual output with `server.host.bandwidth_limit(0, 0)` before client creation:

```text
START mode=workaround channels=4 workaround_before_connect=true
SAMPLE elapsed_s=0.51 throttle_limit=32/32 sent=31 received=30
SAMPLE elapsed_s=1.01 throttle_limit=32/32 sent=61 received=60
SAMPLE elapsed_s=1.51 throttle_limit=32/32 sent=91 received=90
SAMPLE elapsed_s=2.01 throttle_limit=32/32 sent=121 received=120
RESULT mode=workaround elapsed_s=2.26 minimum_limit=32 final_limit=32 scale=32 sent=136 received=135
```

The exact frame counts can vary by one. The relevant result is the client-observed minimum **1 versus
32** during the same approximately two-second unreliable-send run. The defect case's return to 32 at
the next epoch is the known throttle oscillation, not a recovery of the incorrect server setup; it
already discarded most packets during the clamped interval.

## Proposed upstream fix

The one-line fix is to put the channel expression and incoming bandwidth back in their declared
positions:

```diff
- RETURN_IF_ERROR(host->create_host_bound(bind_ip, p_port, p_max_clients, 0, p_max_channels > 0 ? p_max_channels + SYSCH_MAX : 0, p_out_bandwidth));
+ RETURN_IF_ERROR(host->create_host_bound(bind_ip, p_port, p_max_clients, p_max_channels > 0 ? p_max_channels + SYSCH_MAX : 0, p_in_bandwidth, p_out_bandwidth));
```

Upstream should add coverage that verifies both the host channel limit and advertised incoming
bandwidth, including zero/unlimited and explicit finite values.

**Title**

> ENetMultiplayerPeer.create_server passes max_channels as incoming bandwidth and drops p_in_bandwidth

**Body**

> ### Tested versions
>
> - Reproducible in Godot `4.8.dev7.official.c971f93e7`
>   (`c971f93e7e76b0ef919bf6009e7b868bea04db7f`).
> - The same source is present on `master` at
>   `65e8d16951d6963cb3984c090e45f40d1ba5f704` (source-inspected, not run).
>
> ### System information
>
> Windows 11 10.0.26200, Godot 4.8.dev7 official, headless, loopback ENet. The same source defect is
> platform-independent.
>
> ### Issue description
>
> `ENetMultiplayerPeer::create_server(port, max_clients, max_channels, in_bandwidth,
> out_bandwidth)` calls `ENetConnection::create_host_bound` with the last three arguments in the
> wrong positions:
>
> ```cpp
> host->create_host_bound(bind_ip, p_port, p_max_clients, 0,
>         p_max_channels > 0 ? p_max_channels + SYSCH_MAX : 0, p_out_bandwidth)
> ```
>
> The callee order is `max_peers, max_channels, in_bandwidth, out_bandwidth`. Therefore the channel
> limit is always zero (ENet maximum), `p_in_bandwidth` is ignored, and a nonzero `max_channels`
> becomes a tiny incoming bandwidth. With four application channels the server advertises 6 B/s.
> At the next one-second ENet bandwidth epoch, the client's peer throttle falls from 32 to 1. Because
> counter positions 0 and 1 pass, the client discards about 30/32 unreliable packets before sending.
>
> Expected: `max_channels` controls channels and `in_bandwidth` controls incoming bandwidth.
> Actual: explicit channels create a tiny bandwidth limit and severe client-to-server unreliable
> loss on loopback.
>
> The likely fix is:
>
> ```diff
> - create_host_bound(bind_ip, p_port, p_max_clients, 0, channel_count, p_out_bandwidth)
> + create_host_bound(bind_ip, p_port, p_max_clients, channel_count, p_in_bandwidth, p_out_bandwidth)
> ```
>
> ### Steps to reproduce
>
> 1. Download and unzip the attached MRP.
> 2. Run the defect case:
>    `godot --headless --max-fps 60 --path . --script main.gd`
> 3. Observe `minimum_limit=1` after about two seconds of unreliable sends.
> 4. Run the workaround case:
>    `godot --headless --max-fps 60 --path . --script main.gd -- --workaround`
> 5. Observe `minimum_limit=32`. The workaround only calls
>    `server.host.bandwidth_limit(0, 0)` after `create_server` and before client creation.
>
> Representative result:
>
> ```text
> RESULT mode=defect elapsed_s=2.26 minimum_limit=1 final_limit=32 scale=32 sent=136 received=59
> RESULT mode=workaround elapsed_s=2.26 minimum_limit=32 final_limit=32 scale=32 sent=136 received=135
> ```
>
> ### Minimal reproduction project
>
> Attached: `godot-enet-create-server-bandwidth-mrp.zip`. It contains only `project.godot` and one
> `SceneTree` script. The script creates server and client peers in one process on `127.0.0.1`, polls
> both, sends one 512-byte unreliable packet per frame, and prints the client peer's
> `PEER_PACKET_THROTTLE_LIMIT`. No addons or external assets are used.
